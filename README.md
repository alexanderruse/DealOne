# DealOne

**Set your price. Catch your moment.** A Grok-powered shopping agent that watches prices and completes one purchase within rules you explicitly authorize.

Built for a Capital One hackathon concept using **Grok / xAI**, **Tiger Data**, and **Vultr Kubernetes Engine**. This implementation uses a controlled demo storefront and **simulated virtual card payments**. It does not issue Capital One cards, charge real money, or purchase from third-party retailers.

## Run locally

Requires Docker with Compose. Node and Python do not need to be installed on your host.

```sh
cp .env.example .env
docker compose up -d --build
```

Open **http://localhost:3001**. Port 3001 avoids the previous hackathon project's port 3000. Local data lives in the `dealone_database` Docker volume; ordinary restarts preserve it.

Set `XAI_API_KEY` and a sponsor-enabled `XAI_MODEL` in `.env`, then recreate `api` and `worker` to enable Grok. Without a key, the manual rule form and complete simulated purchase flow still work; the interface explicitly identifies Grok as unconfigured.

### Demo in 90 seconds

1. Select **Watch this item** on the headphones.
2. Set the **all-in maximum to $180**, review the draft, and activate automatic purchasing.
3. Open **Demo controls**, enter the local token `local-demo-admin`, and change the headphones' item price to **$159**.
4. Wait for the worker's next scan (10 seconds). The browser worker opens checkout, revalidates your rules, and submits the simulated order.
5. Open **Activity**: the receipt is **$168.94** including simulated Massachusetts sales tax. The watch becomes `purchased`.

The catalog and initial price history are synthetic demo data. A price change in Demo controls is real database state used by the monitoring worker; the receipt is generated by the checkout flow, not fabricated by the frontend.

## Architecture

```text
Browser → Traefik / HTTPS → React + Caddy → FastAPI
                                             │
                                         Tiger Cloud
                                             │
                                    Monitoring worker
                                             │
                                 Playwright → Demo checkout
                                             │
                              Simulated payment + merchant ledger
```

- React, TypeScript, Vite, Tailwind, and a shadcn-style Radix/CVA button component.
- FastAPI, Pydantic, SQLAlchemy, Alembic, and Psycopg 3.
- Official `xai-sdk` for structured rules and bounded function calling. Grok cannot activate permissions, override limits, view payment credentials, or navigate a browser freely.
- Tiger Cloud in production; TimescaleDB in local Docker. Price observations use a hypertable. All money uses integer cents.
- Two web and two API replicas, one worker with a Recreate update strategy, a load balancer, Traefik, and cert-manager in Kubernetes. Database storage stays in Tiger Cloud.
- Separate API and browser-worker images share backend source. The worker installs Chromium matching its pinned Playwright package.

## Purchase guarantees

Permissions start as drafts. Activation authorizes one item with a specific variant, seller, condition, currency, all-in maximum, and expiration. Every checkout rechecks these constraints, stock, and the prepared total. A changed checkout total requires review.

Orders have a unique permission reference. The merchant ledger and simulated payment have unique order references. Permission and product row locks serialize competing purchases; a session advisory lock prevents multiple browser executors for the same order. The simulated merchant order, authorization, stock decrement, receipt, and permission completion commit atomically.

On a restart, the worker checks the merchant ledger before submitting. A timeout with a committed receipt is reconciled; an unknown failure without a receipt pauses for user review. No blind payment retry occurs. Login, CAPTCHA, and real payment authentication are outside this controlled adapter; future adapters must report these as required user actions.

Browser contexts send only an internal worker credential, and navigation is restricted to the configured demo storefront origin. Public API users cannot call the storefront submission routes. Sessions are isolated with signed, HttpOnly, SameSite cookies; production uses Secure cookies. This demo does not provide account recovery: clearing cookies creates a new workspace.

## Deploy to Vultr

See **[deployment setup](docs/DEPLOYMENT.md)** for exact GitHub secrets, workflows, DNS, and rollback steps. The existing registry is `thegoatsdockerregistry` (`369a6c53-fd50-4fe2-93d6-a151ec00c845`). The deployment targets **dealone.work**, **New York/New Jersey (`ewr`)**, and **two Optimized Cloud nodes**.

Infrastructure provisioning is manual and starts with a read-only cost quote. Application deployment never provisions a cluster. Configure the required secrets and variables before using either workflow; no cloud resources are created by cloning or running this project locally.

Domain DNS can be automatic: add `PORKBUN_API_KEY` and `PORKBUN_SECRET_API_KEY` with API access enabled for `dealone.work`. Provisioning and deployment then synchronize the root website record to Traefik's load balancer, preserving email records and subdomains. Without these keys, the workflows print manual DNS instructions. See the deployment guide for setup and a standalone DNS refresh workflow.

## Verify

```sh
docker compose exec -T api python -m pytest -q tests
python3 -m unittest discover -s scripts/tests -q
kubectl kustomize infra/k8s
```

For browser acceptance tests, install frontend dependencies in Node 22 and matching Playwright Chromium, then run `npm run test:e2e` in `frontend`. Tests exercise real API state and the browser worker; backend tests use an isolated temporary database schema.

`Checks` runs frontend build/audit, the Docker stack, backend integration tests, and browser tests. `Deploy DealOne` runs only after successful main-branch push checks once `VULTR_CLUSTER_ID` is configured. Manual redeployment also supports previous image tags.

Health endpoints: `/api/health/live`, `/api/health/ready`, `/api/health/worker`. Interactive API reference: `/docs` on the internal API service (not routed by the public web server).

## Initial-version boundaries

- Payments are simulated and the only merchant is the controlled storefront.
- Price monitoring reads that storefront's database; external retailer ingestion is a future adapter.
- Notifications are in-app. Resend configuration is reserved for a later email opt-in feature; providing its key alone does not enable email delivery.
- Grok needs a valid sponsor key, enabled model, and API credits; local automated tests do not consume API credits.
- Public deployment, live Grok connectivity, and DNS/TLS require your configured accounts and credentials.
